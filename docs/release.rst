=======
Release
=======

This page is for maintainers cutting a new release. It isn't something a contributor opening a PR needs to read.

Versioning
==========

calendaring-jmap has no release branches: every release ships from ``main``. The version number comes entirely from the git tag, read at build time by ``hatch-vcs``; nothing in the source tree stores it. ``src/calendaring_jmap/_version.py`` is generated during the build and isn't tracked in git.

Cut a release
=============

#. Confirm ``main`` is up to date and its CI is green.

   .. code-block:: bash

       git checkout main
       git pull

#. Build the :ref:`change log <change-log>` from the pending fragments in ``news/``, replacing ``1.2.0`` with the real version:

   .. code-block:: bash

       towncrier build --yes --version 1.2.0

   This writes the new section into ``docs/changelog.rst`` and deletes the fragments it consumed. Review the diff; towncrier sorts entries alphabetically within each category, not in the order the fragments were added.

#. Commit directly to ``main``. This one commit is the exception to :ref:`commits-and-prs`'s one-PR-per-change rule: it's a mechanical, maintainer-only step with nothing for a reviewer to meaningfully review.

   .. code-block:: bash

       git add docs/changelog.rst news/
       git commit -m "chore: build 1.2.0 changelog"
       git push

#. Tag the commit you just pushed, and push the tag:

   .. code-block:: bash

       git tag v1.2.0
       git push origin v1.2.0

Pushing the tag triggers the ``release`` GitHub Actions workflow: it runs the full test suite, builds the package, publishes to PyPI via trusted publishing (no stored token), and creates a GitHub release with autogenerated notes. Nothing past the tag push is manual.

Read the Docs builds the new version automatically from the same tag push; no separate step is needed there.

Maintainer access
=================

Releasing calendaring-jmap requires:

``Admin`` access to the `GitHub repository <https://github.com/pycalendar/calendaring-jmap>`_
    Needed to push directly to ``main`` and push tags.
``Owner`` or ``Maintainer`` access to the `PyPI project <https://pypi.org/project/calendaring-jmap/>`_
    PyPI publishing uses `trusted publishing <https://docs.pypi.org/trusted-publishers/>`_ (OIDC), configured against this repository's ``release`` workflow and its ``pypi`` environment; no PyPI API token is stored anywhere. A PyPI account with access can revoke or reconfigure this.
``Maintainer`` access to the `Read the Docs project <https://app.readthedocs.org/projects/calendaring-jmap/>`_
    Needed to manage the Read the Docs build configuration itself, though a normal release build needs no manual action there.
